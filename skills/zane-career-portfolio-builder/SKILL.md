# 职业资产系统构建

先判断用户需要哪些招聘载体，再组织生产；不默认每个人都需要网站、知识库、Word、信息图或同样的页面数量。

完整项目先继承[统一运行模型](../zane-career-assets/references/operating-model.md)的五层真源。不要把简历、网站和多语言版本当成三次独立创作；先解决共同事实与招聘判断，再生成各载体投影。

本 Skill 负责完整项目生产；`zane-career-assets` 是面向所有求职自然语言的统一入口。由总控发起时，继承 `zane-career-assets-state.json` 与交接包，不自行将未审核阶段视为已通过。

## 总流程

按 `Define → Retrieve → Model → Position → Select → Allocate → Produce → Verify → Release → Learn` 执行。

### 1. Define

确认目标岗位、候选人层级、阅读者、渠道、公开边界、截止时间、技术条件与完成证据。额外锁定当前载体要促成的决定、下一环和最终招聘结果；区分用户真正需要的是简历、作品集网站、深读案例、作品画廊、离线文档还是其中组合。面试前的材料不承担后续尽调的全部任务，可后置事实不自动阻断当前候选版；只有重大误导、法律／合规／隐私风险或直接改变当前招聘判断的事实才阻断成稿。

### 2. Retrieve

在独立项目目录建立本次所需的最小工作区。随附 starter 只提供中性的事实台账、状态、案例工作稿和 manifest，不包含可发布网页骨架；网站必须从当前用户的证据关系与视觉人格重新生成。收集旧简历、岗位描述、项目材料、数据、作品、组织信息、反馈和审美参考；旧成品只作为资料与失败证据，不直接套用。

### 3. Model

建立事实台账：正式职位、时间、业务问题、本人控制范围、协作方、动作、结果、统计期、来源、证据等级、公开性和冲突。先解决冲突，再生成任何招聘主张。

### 4. Position

从“岗位需要解决的问题 × 用户已证明的能力 × 同级候选人的区分点”得出定位。愿望、人格标签和通用岗位定义不能替代证据。

### 5. Select

选择能证明不同判断的经历：主案例证明最关键责任；次案例补足另一能力或责任阶段；项目索引证明广度；重复、越界或无法公开的材料降级。案例不按公司知名度或渠道数量机械排序。

### 6. Allocate

建立跨载体地图：简历负责快速筛选，网站负责阅读选择，深读案例负责判断与现场，作品页负责可见产物，面试负责敏感追问。硬事实共用同一台账，表述和信息密度按载体任务变化。

同时建立主张图：每条核心主张连接到支持证据、出现载体、目标读者和下一步行动。找不到证据或承接位置的主张不得只靠文案强化。

### 7. Produce

- 简历交给 `zane-career-resume-builder` 独立主持；
- 网站交给 `zane-career-portfolio-website-design` 独立主持；
- 深读稿按业务问题、判断、动作、代价、边界与证据展开；
- 只有关系、顺序、对比或趋势难以用正文说明时才制作信息图。

主 Skill 收回各模块结果，更新事实台账、决策合同、manifest 和下一阶段输入。

用户确认、否决、事实纠正或稳定偏好出现时立即更新决策账本，并按影响范围同步下游；不等到项目结束统一补记。修改循环遵循[决策记忆与变更控制](../zane-career-assets/references/change-control.md)。

任一专项 Skill 进入可投递或可部署成品生产前，先运行 `zane-career-assets` 的对应状态检查。文案、结构或视觉方向尚未获得用户明确确认或明确放弃审核时，不得直接出成品。

### 8. Verify

从正式生成源和交付目录验收，不从临时候选继承结论。检查事实一致性、职责归因、敏感数据、桌面与手机、全部文档页、图片、锚点、链接、二维码、无障碍和降级状态。

运行 `scripts/validate_portfolio.py` 做结构检查；机器通过不替代真实页面和文档实看。验收按[职业资产验收模型](../zane-career-assets/references/evaluation-model.md)覆盖事实、招聘、语言、视觉、交互与发布六层。

跨项目复盘或多人协作时，额外比较简历与网站的结构签名。若不同项目的入口形态、首个证据、主阅读轴、案例关系、数字角色和收束方式有四项以上相同，且差异主要是文字与颜色，记为模板回流并重开对应载体；每个项目都应从自己的目标、证据和审美重新推导结构。

### 9. Release

区分候选、用户确认、待部署、已部署和真实招聘反馈。只有公开 URL 与线上资源实测通过才称为已部署；只有投递、面试或招聘反馈发生，才称为进入现实验证。

状态按闸门单向晋级且互斥：`候选 → 用户确认 → 待部署 → 已部署 → 现实反馈`。没有用户确认时，即使目录可静态部署，也仍是候选，不能写“候选／待部署”。简历的正式投递状态与网站部署状态分别记录，不用一个总标签混写。

README、manifest、QA 摘要和交付说明都使用带对象的独立字段，例如`简历：候选版；网站：完整站候选；部署：未部署；现实反馈：未发生`。即使两个状态都真实，也不写`状态：候选版／完整站候选`之类的斜杠总标签，避免读者误以为它们是同一资产的并列状态。

### 10. Learn

记录跨用户可复用的判断机制与失败条件。个人颜色、版式、公司、数字、职位和文案只留在项目配置或匿名测试样本，不进入 Skill 默认值。只有在不同职业、证据形态和市场中仍能解释问题并导出行动的方法，才回写 Skill。

## 原创边界

本套件的方法来源是实际职业资产项目中的问题拆解、失败复盘和验证结果。可以使用信息架构、证据分级、约束设计、假设检验等公共知识，但不得复制第三方 Skill 的具体流程、措辞、模板或资产。来源与原创性边界见 [references/public-risk-and-provenance.md](references/public-risk-and-provenance.md)。

## 完成标准

- 用户获得符合其岗位、证据与审美的成品，不是替换姓名的模板；
- 每条主张可追溯，每个载体有独立任务；
- 简历、网站与深读案例互相承接但不重复全文；
- 生成源、成品、资产、合同、manifest 和 QA 齐全；
- 发布状态与现实反馈如实区分。

## 发布状态

套件为 `v0.7 beta`，可独立完成职业资产从 0 到 1 的规划、生产、验收和交付。它不替用户虚构事实，不替用户确认成品，也不把某个项目的结果复制成其他人的默认答案；具体岗位、证据和审美仍由当前项目决定。
